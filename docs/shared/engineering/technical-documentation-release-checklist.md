# 技术文档发布质量清单

> **适用读者：** 文档工程师、研发、测试、产品与发布负责人<br>
> **目标：** 在发布前检查技术文档的准确性、完整性、一致性、可读性与可追溯性<br>
> **使用方式：** 按风险裁剪；不适用项应注明理由，不以勾选代替证据<br>
> **材料类型：** 通用个人方法论样例，不替代产品质量流程或合规评审<br>
> **文档更新：** 2026-11-01

## 1. 发布原则

- **技术事实由责任人确认。** 文档编辑或语言优化不构成技术批准。
- **检查结论要有证据。** 重要规格应能回到有效来源，操作步骤应有验证记录。
- **未决项不能伪装成已完成。** 记录状态、责任人、影响和放行决定。
- **门禁按风险分层。** 高风险内容采用更严格的评审与验证；不适用项说明理由。

## 3. 输入与追溯

- [ ] 文档目标读者、使用场景和范围已经明确。
- [ ] 输入资料有来源、版本、批准状态和责任人。
- [ ] 关键规格、接口、限制和安全相关陈述均可追溯到受控来源。
- [ ] 操作步骤关联到实际验证证据，包含必要的环境/版本信息。
- [ ] 草案、待确认项、内部备注和占位内容已清除或明确阻止发布。
- [ ] 未决项已记录责任人、截止/处理计划、用户影响和处置决定。

## 4. 技术准确性

### 适用于规格类文档

- [ ] 数值、单位、符号、范围及类别与批准资料一致。
- [ ] 参数出现时，适用条件、测试条件和必要注释清晰可见。
- [ ] 图表、表格、封装/接口信息与当前产品版本一致。
- [ ] 典型信息、保证范围、限制和示例的性质没有混淆。
- [ ] 引脚、信号、寄存器或接口名称与权威定义一致（若适用）。
- [ ] 警告、注意事项和已知限制在相关操作或数据附近可见。

### 适用于操作指南

- [ ] 前置条件、工具/软件版本、初始状态和权限要求明确。
- [ ] 步骤按执行顺序组织，每个动作使用准确名称。
- [ ] 每个关键阶段都有可观察的预期结果或成功判据。
- [ ] 错误分支、停止条件和升级路径不会诱导读者继续执行不确定操作。
- [ ] 步骤已在声明的环境和版本中执行，例外已记录。

> 以上项目按文档类型选择；不适用时标记为 N/A 并说明理由。列表中的“已检查”需要有来源核对或执行记录支持。

## 5. 完整性与可用性

- [ ] 读者能从标题、目录和章节层级识别文档范围。
- [ ] 目标任务的前置条件、执行步骤、预期结果和限制均齐备。
- [ ] 缩写、术语和首次出现的关键概念已解释或可链接到定义。
- [ ] 警告、限制、注意事项与相关内容相邻，而非仅集中在文末。
- [ ] 图表有编号、标题、引用和必要的文字说明；关键信息不只存在于图片中。
- [ ] 链接和交叉引用指向当前有效页面/版本。
- [ ] 目标读者或代表性评审者完成了至少一项关键任务走查（按风险适用）。

## 6. 一致性与版本

- [ ] 产品名称、版本、术语、缩写和大小写符合团队规范。
- [ ] 同一发布范围内，规格、限制、步骤和示例没有冲突。
- [ ] Datasheet、User Guide、Release Notes 与支持内容的关联信息一致（按范围适用）。
- [ ] 文档版本与对应产品版本关系明确。
- [ ] 变更记录说明本次变更、影响范围和替代关系。
- [ ] 历史正式版本可追溯，旧版入口不会被误认为当前版本。
- [ ] 翻译版本已同步关键事实、警告、限制和版本信息（按范围适用）。

## 7. 构建、呈现与交付

- [ ] 源文件通过格式、链接、必需章节和引用检查。
- [ ] 导出文件/网页可以打开，目录、字体、代码、图表和表格呈现正常。
- [ ] 页面在目标阅读环境下可用；重要内容不依赖颜色单独传达。
- [ ] 文件名、版本号、元数据和下载入口符合发布规则。
- [ ] 实际发布包与已批准版本一致；临时文件、草稿和内部评论已排除。
- [ ] 发布权限、公开范围和反馈入口已确认。

## 9. 建议的最小发布门禁

如果团队尚无统一流程，可先对每次公开发布执行以下四项：

1. 研发确认高风险技术事实和适用版本；
2. 测试或目标执行者验证关键用户任务；
3. 文档负责人检查跨文档一致性、链接和最终呈现；
4. 发布负责人确认审批版本与实际发布包一致，并保存记录。

自动化适合查找可机械判定的问题，例如断链、格式、必需字段和版本元数据；它不能代替技术确认或用户任务验证。
